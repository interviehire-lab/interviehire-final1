## 1. Scheduling automations (new)

**WhatsApp confirmation** on both the recruiter's schedule action and the
candidate's self-reschedule — `backend/app/utils/twilio_client.py`. Supports
Twilio Content Templates (`ContentSid`/`ContentVariables`, required for a
business-initiated WhatsApp message outside an open 24h session) with a freeform-
text fallback for Sandbox testing. Prefers a scoped Twilio API Key over the master
Auth Token when both are configured.

**Pre-interview reminder job** (email + WhatsApp + robocall, ~30 min before
start) — `backend/app/jobs/reminders.py`, modeled on the existing
`app/jobs/retention.py` pattern (CLI + internal-secret-gated endpoint,
`POST /api/internal/run-reminders`, dry-run by default). Idempotent via two new
`Applicant` columns (`screening_reminder_sent_at`/`functional_reminder_sent_at`).

**Known unverified gap:** the WhatsApp Content Template variable ordering
(`{"1": name, "2": role, "3": time, "4": link}`) is a guessed default — it has
**not** been confirmed against the actual approved template text in the Twilio
Content Editor. Verify before relying on this in production; see the comments in
`twilio_client.py` and the `TWILIO_WHATSAPP_CONFIRMATION_CONTENT_SID`/
`TWILIO_WHATSAPP_REMINDER_CONTENT_SID` env vars.

**To go live:** fill in `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` (or
`TWILIO_API_KEY_SID`/`TWILIO_API_KEY_SECRET`), `TWILIO_WHATSAPP_FROM`,
`TWILIO_VOICE_FROM`, and the two Content SID vars in production env. Point a
Railway Cron Job (or any external pinger) at
`POST /api/internal/run-reminders?dry_run=false` with header
`x-internal-secret: <INTERNAL_SERVICE_SECRET>`, every ~5 minutes.

## 2. Timezone correctness — IST everywhere

**Root cause found and fixed:** the whole app stored/labeled scheduled times as
UTC, but every datetime picker copied typed digits with zero conversion — "6:31
AM" always meant literally 6:31 AM UTC (12:01 PM IST), not what anyone typed.
This was caught because a real candidate's interview time was off by 5.5 hours.

- `backend/app/utils/timezones.py` (new): `parse_scheduled_datetime()` treats a
  naive (no-offset) input as IST and converts to UTC; an already-tagged
  UTC/offset string is trusted as-is. `to_ist()`/`format_ist()` for display.
- Applied to both parse sites (`jobs.py` schedule, `public.py` reschedule) and
  every display site (WhatsApp confirmations, the iCal confirmation email, the
  reminder email, the "1 PM next day" auto-default, the `/confirm` link's HTML
  page) — all now say IST, not UTC.
- `dashboard/public/reschedule.html` — candidate picker now does its own IST↔UTC
  math (independent of the viewer's device timezone) rather than trusting
  `new Date()`'s local-offset parsing.
- `dashboard/src/dashboard/resume-analysis.ts` (recruiter schedule modal) — same
  fix, **plus removed a decorative "Time Zone" dropdown that listed 10 timezones
  but never actually did anything** (picking "America/New_York" silently changed
  nothing — a real, separate bug). Replaced with a static "Asia/Kolkata — all
  times are IST" label, which is what was actually happening all along.
- `interview-engine/apps/web/.../WaitingRoom.tsx` — the "Scheduled for X" lobby
  text now shows IST instead of the candidate's device timezone.
- `backend/tests/test_timezones.py` (new, 7 tests, no DB needed) covers the
  parse/display/round-trip logic directly.

## 3. Candidate portal bug fixes

- **Reschedule silently didn't sync to the engine for screening-stage
  candidates.** `public_reschedule_interview`'s `functional_status` branch called
  `sync_applicant_to_ai()`; the `screening_status` branch (`elif`) did not. A
  screening-stage reschedule updated the backend row correctly but the candidate
  room kept showing the OLD time indefinitely, reading a stale
  `InterviewSession.scheduledAt`. Fixed in `backend/app/routers/public.py`.
- **`reschedule.html`/`talent-finder.html` hardcoded the wrong local-dev API
  port** (`:8002`, nothing listens there — every other config in the repo uses
  `:8000`). Every local reschedule attempt failed with "Link not valid" for a
  reason unrelated to the token itself. Fixed.
- **Avatar iframe pointed at a dead URL when unconfigured.** `NEXT_PUBLIC_AVATAR_URL`
  is deliberately blank in local dev (no UE5 Pixel Streaming server runs
  locally), but the code fell back to `http://localhost:80`, which nothing
  serves, and embedded it in an iframe unconditionally — producing a raw
  "localhost refused to connect" browser page bleeding through the room UI. Now
  shows a graceful "Avatar preview unavailable" placeholder when no real avatar
  source exists (`page.tsx`, `AVATAR_CONFIGURED`/`hasRealAvatar`).
- **Self-view voice highlight** — the candidate's own video tile now glows when
  their voice is detected (Web Audio `AnalyserNode` over the existing mic track,
  no extra permission prompt), so candidates can visually confirm their mic is
  being picked up.
- **Browser STT failed 100% silently on any error.** `useTranscript.ts`'s
  `rec.onerror` was a complete no-op — unsupported browser, denied permission, or
  (the actual cause hit during testing) a `network` error reaching Chrome's cloud
  speech backend all produced zero trace anywhere, just a silently empty
  transcript that only surfaced as "Transcript unavailable" in the final report.
  Now logs to console, tracks `sttStatus`/`sttError`, and — **demo/debug mode
  only** (`sessionId === 'demo-session'` or the `🐞 Debug` toggle) — shows a live
  caption bar with real-time recognition output, so a broken STT path is visible
  during testing instead of only discovered after the interview ends.
- `EARLY_ENTRY_MS` deduplicated into `@interviehire/shared` (was hand-synced
  between the candidate room and the engine route, a drift risk).
- Candidate room now honors the per-job `proctoring` toggle, which was already
  reaching the client but never actually read (proctoring ran unconditionally
  regardless of the recruiter's setting).

**Still open / not investigated this session:** a demo-mode test report showed
the primary evaluator (`reportEngine: "transcript_llm"`) producing a correct,
populated result, while the *second*, nested structured evaluator
(`structured.evaluationEngine: "aviral_openrouter"`) came back entirely empty/
zeroed (`overallScore: 0`, all arrays `[]`) despite the same transcript being
available to both. Not yet root-caused — flagged to the user, not yet actioned.

## 4. Backend test suite (new)

First real test infrastructure exercising auth → job → resume → schedule →
reschedule → automations, all via `TestClient` against a disposable Postgres.

- `backend/tests/conftest.py` (new — first shared fixtures in this repo's test
  suite): DB engine/session, `TestClient`, `mocked_externals` (patches every
  Twilio/Google Calendar/Resend/DeepSeek call site at its exact import path —
  see the fixture's docstring for why each needs patching differently),
  `signup_and_onboard()` helper.
- `backend/tests/test_full_flow.py` (new) — the main flow: signup → onboarding →
  create job → upload a resume (plain `.txt`, no PDF needed) → schedule →
  DB-state check that the engine's shared tables got synced → candidate
  reschedules → `POST /api/internal/run-reminders` returns 200 and actually
  fires (mocked) → idempotency check. Plus auth-guard edge cases.
- `backend/tests/test_engine_reachability.py` (new) — boots the *real* Fastify
  engine (`apps/api`) as a subprocess, hits `/health`, `/api/interview/demo-session`
  (idempotency), and confirms `GET /api/interview/sessions/:id` actually serves
  what the backend synced. Kept in its own file since it's heavier/more
  environment-dependent than the hermetic suite.
- `backend/tests/test_timezones.py` (new) — pure-logic IST tests, no DB needed.
- `backend/requirements-dev.txt` (new) — `pytest`, `httpx`.

**Fixed a blocking issue in the 3 pre-existing test files**
(`test_data_rights.py`, `test_privacy_api.py`, `test_retention.py`): their
`Base.metadata.drop_all(bind=_engine)` teardown broke the moment a real
disposable Postgres with the engine's full Prisma schema was actually used (as
their own docstrings instruct) — Postgres refuses to drop `InterviewSession`
while Prisma-only tables (`TranscriptEvent`/`InterviewTranscript`, not in
SQLAlchemy's `Base.metadata` at all) still FK-reference it. Fixed by only
dropping backend-owned tables. A second-layer issue (`metadata.drop_all(tables=...)`
still sweeping ALL Postgres ENUM types regardless of the table filter) required
switching to per-table `.drop()` calls. A third, non-deterministic row-count bug
in `test_data_rights.py` was diagnosed as far as "the query behaves correctly in
isolation but not in file order" and handed off as a background task
(`task_aea3641d`) — **that task has since completed and the fix is already
included in this commit** (verified: 3 repeated fresh-DB runs all pass, plus the
full 31-test suite together).
